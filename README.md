# Senara Dental Group: CRM Data Pipeline (demo)

> Fictional company, 100% synthetic data. A portfolio rebuild of a real
> production WhatsApp-CRM ETL pipeline I built and operate at my day job,
> using the same architecture and techniques on an entirely fictional
> company, brands, and data.

A small, standalone data-engineering pipeline: Bronze -> Silver -> Export,
orchestrated by a single CLI, idempotent by construction, with synthetic data
generated fresh on every clone.

## Why it's interesting

- **Idempotent by construction.** Every step can be re-run any number of times for
  the same date without duplicating or corrupting data: delete-insert on the silver
  layer, an audit-logged idempotent GSheet append, a key-matched patch instead of a
  blind append on CSV export.
- **A real bug caught by its own test.** Patching a CSV export by key silently
  duplicated every row on re-run, because a phone-number key round-trips through
  CSV as `int64` while the freshly computed frame has it as `str`. Fixed, and now
  guarded by a regression test (`tests/test_export.py`) so it can't come back quietly.
- **One brand deliberately never migrated.** `mira` still runs the old
  recency-only dedup while the other three brands use priority-rank with a
  deterministic tie-break. Both strategies live side by side in
  `pipeline/transform.py`, routed per brand, instead of being smoothed into one
  "obviously correct" function.
- **A cell-capacity guard on the optional Sheets export**, warning before a write
  gets near Google's hard 10-million-cell-per-sheet limit, instead of finding out
  mid-run.
- **Zero setup.** `pip install`, one command to generate synthetic data, one
  command to run: no real database, no real credentials, no network calls, by
  default.

## Stack

Python, pandas, DuckDB (embedded, multi-schema), Faker, pytest. Optional: Google
Sheets API (off by default).

## Quickstart

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m data_gen.bootstrap        # generates synthetic reference + conversation data
python -m pipeline.pipeline --dry-run
python -m pipeline.pipeline         # real run, defaults to the latest date with inbound activity

pytest tests/ -q
```

## Architecture

```
data_gen/ --generates--> data/incoming/*.csv --(extract.py)--> bronze.*
                                                                   |
                                                        (transform.py) -> silver
                                                                   |
                                    +------------------------------+------------------------------+
                                    v                                                              v
                          silver.rpt_main (detail)                                      silver.rpt_queue (deduped)
                                    |                                                              |
                                    +----------------------------- export.py ----------------------+
                                                      |                                  |
                                            data/exports/*.csv                 GSheet (optional, off by default)
```

`pipeline/pipeline.py` orchestrates all three steps with a CLI: a date argument,
`--force`, `--skip-extract`, `--only-export`, `--step`, `--dry-run`. Every step
logs to `audit.pipeline_runs`, and a failure sends an (optional, self-skipping)
email alert.

## Project layout

- `pipeline/config.py`: single source of configuration (brands, paths, feature flags)
- `pipeline/extract.py`: bronze loader (skip-if-exists-else-force / always-replace)
- `pipeline/transform.py`: the six techniques worth reusing (see module docstring)
- `pipeline/export.py`: patch-by-key CSV/GSheet export
- `pipeline/tagging.py`: standalone typo-canonicalization, not wired into the pipeline, on purpose
- `pipeline/pipeline.py`: CLI orchestrator
- `data_gen/`: synthetic data generation
- `docs/adr/`: why things are built this way
- `tests/`: unit tests per module, plus one end-to-end idempotency test

## Tests

```bash
pytest tests/ -q
```

15 tests: phone normalization, direction detection, response-time calculation,
new-contact detection, both dedup strategies, tag canonicalization, patch-by-key
(including the CSV round-trip regression above), and a full
extract-transform-export idempotency check.

## Privacy

**Senara Dental Group, and every brand, agent, and customer name and phone number
here, is entirely fictional.** This is a from-scratch rebuild of the architecture
and techniques behind a real pipeline I built and operate professionally. No code,
data, credentials, or identifiers were copied from that system. Every row of data
in this repo is generated by `data_gen/` at setup time.
